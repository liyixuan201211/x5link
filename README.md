## ⚠️ 启动方式：必须用 LaunchServices（`open`），别直接执行 bundle 里的二进制

这是踩过一个大坑之后写下的，**症状极具误导性**，请务必照做：

```bash
# ✅ 对的：走 LaunchServices，摄像头权限才会正常给
open -a /Users/imac/南客松-v2/x5-link/X5Link.app --args web --port 8765

# ❌ 错的：直接执行内部二进制 —— 摄像头永远不出帧
./X5Link.app/Contents/MacOS/X5Link web --port 8765
```

**错误那条路会怎么表现**（我们为此查了很久）：

* 设备**能枚举**：`ffmpeg -list_devices` 正常列出 `[0] Insta360 X5`
* 格式**能查询**：报错信息里能列出它的 `2880x1440@30` 等全部模式
* 但**一帧都收不到**，而且**不报任何错**：打开设备、打印一句
  `Overriding selected pixel format to use uyvy422`，然后就永远挂在那里
* **换哪台相机都一样**（连内置 FaceTime 相机也是 0 帧）、换像素格式
  （nv12/uyy422）、换分辨率（2880×1440 / 1920×1080）、不指定尺寸 —— **全都 0 帧**
* 根因是 **TCC 摄像头权限没给到**。原生启动器会自述状态：
  `[X5Link] 摄像头权限：status=0 (仍未决定)`
  （`0` = 未决定，授予会是 `3`）。**macOS 在没授权时的行为和"驱动坏了"长得一模一样**：
  能枚举、不能收帧、不报错。

**判断方法**：`open` 起，然后

```bash
curl -s http://127.0.0.1:8765/status
# frames 在涨、last_frame_age_s ≈ 0  → 成功
```

> 补充：直接在自己 shell 里跑 ffmpeg 抓帧**同样会 0 帧**（权限链不同），
> 所以"我手动抓也没帧"并不能证明相机坏了。

## ⚠️ 采集侧三个加固（`x5link/web.py`，2026-09-22）

原来 `MjpegSource` 只有"**ffmpeg 退出**才重拉"，兜不住下面两种死法；现在都补上了：

| 死法 | 症状 | 现在怎么办 |
|---|---|---|
| **设备序号会变** | AVFoundation 枚举顺序**不稳定**（实测到过 `[0]=Insta360/[1]=FaceTime`，过一会儿反过来）。序号只解析一次的话，顺序一翻 ffmpeg 就打开错误的设备（FaceTime 不支持 2880×1440），报 `Selected video size is not supported`，然后**永久**不出帧 | 每次起 ffmpeg 前 `_resolve_index()` **按名字重新解析序号** |
| **ffmpeg 活着但不出帧** | `stdout.read()` **永久阻塞**，循环再也回不到重启逻辑 —— 表现是"服务在跑、状态正常、画面不动" | `_watch` 看门狗：首帧 **12s** / 稳态 **3s** 没有新帧就 kill 掉重来 |
| **错误全被吞掉** | `stderr=DEVNULL` + `except: pass`，**一行日志都没有**，根本没法查 | ffmpeg 的 stderr 落到日志文件；`-loglevel` 用 **warning** 而不是 error（要排的 `Selected pixel format/size ... not supported` 恰好都是 warning，用 error 会得到 0 字节日志） |

`/status` 现在还会自述 `device_index` / `restarts` / `notes`（序号是否变过、看门狗何时动的手），
出问题先看这三个。

## 一、取流路线：USB Webcam（UVC）模式

X5 要「实时画面进电脑」，只有这一条路能满足体感玩法：

| 路线 | 可行性 |
|---|---|
| **USB Webcam（UVC）** | ✅ 官方支持，一根线，机内已拼接+防抖，延迟最低 |
| HDMI 采集卡 | ❌ X5 没有 HDMI 输出 |
| WiFi RTMP 推流 | ⚠️ 能用，但延迟通常 1–3 秒，做不了实时体感 |

依据（影石官方文档）：

- [X系列：相机连接电脑作为 Webcam 会议摄像头](https://onlinemanual.insta360.com/x5/zh-cn/operating_tutorials/connect/webcam)
- [Webcam/网络摄像头使用 OBS 推流全景直播教程](https://onlinemanual.insta360.com/x5/zh-cn/camera/appuse/obs)

### 操作步骤

1. X5 **开机**（固件升到最新，Webcam 功能需要较新固件）
2. 用**原装数据线**连到电脑
3. 相机屏幕会弹出 USB 模式选单 → 选 **「USB 摄像头」**
4. 跑 `python -m x5link devices`，应该看到多出一个 `Insta360 X5`

### 三个必须知道的官方限制

1. **默认不是全景。** 相机默认可能只给「双视图拼接」或「单镜头」画面。
   必须在采集端把分辨率手动设成 **2880×1440**，才会切到全景 Webcam 2:1 模式
   —— 这正是 `probe` 要验证的第一件事。
2. **Webcam 模式下相机参数不可调。** 分辨率、防抖、FOV、变焦全部由电脑端决定，
   机内设置被覆盖。所以「画质」这一项在 Webcam 路线里没有旋钮。
3. **输出的是等距柱状（经纬图）2:1。** 这对我们是好消息 —— 见文末「与后续步骤的衔接」。

另外两条有用的事实：Webcam 模式下**可以同时给相机充电**（长局不用换电池）；
相机屏幕会**保持常亮**（产品设计如此，短按电源键可手动息屏）。

## 二、快速开始

```bash
cd /Users/imac/南客松-v2/x5-link
PY=../3dgs-lab/.venv/bin/python        # opencv-python 5.0 已装在这个 venv 里

# 0) 先自检，确认工具本身没问题（不需要相机）
$PY -m x5link selftest

# 1) 看设备，确认 X5 被认出来
$PY -m x5link devices

# 2) 试探分辨率：能不能真拿到 2880x1440 全景 2:1，实际帧率多少
$PY -m x5link probe

# 3) 列出相机真正暴露的 UVC 档位（AVFoundation 是唯一可信来源）
$PY -m x5link formats

# 4) 实时预览（这一步就是验收里的「电脑显示玩家画面」）
$PY -m x5link preview

# 5) 预览的同时把本次素材存下来（验收里的「能保存本次游戏素材」）
$PY -m x5link preview --record ~/Desktop/run01.mp4

# 6) 网页端 360° 拖动预览，无畸变 —— 见下面第三节
open -n "$PWD/X5Link.app" --args web --open

# 7) 量端到端延迟：屏幕全屏显示时间戳卡片，把 X5 对准屏幕
$PY -m x5link latency --seconds 15 --evidence /tmp/x5ev
```

> **注意**：`preview` / `latency` / `web` 要读摄像头，请通过 `X5Link.app` 启动
> （原因见第五节）：
> ```bash
> open -n "$PWD/X5Link.app" --args preview --record ~/Desktop/run01.mp4
> ```
> `devices` / `formats` / `probe` / `selftest` 里只有 `probe` 需要相机，
> 其余可以直接跑。

`latency` 怎么用：跑起来后**整块屏幕**会变成黑白卡片，把 X5 架在三脚架上对准这块屏，
让卡片占满画面中间的大部分。工具会实时打印延迟，15 秒后给统计。

> 显示器有 3 块（`Capture screen 0/1/2`）。想把卡片放到外接屏上量，加
> `--window-pos X,Y` 指定卡片窗口的落点。

### 延迟判定标准

`latency` 最后会给一句结论，阈值是这样定的：

| 端到端延迟 | 结论 |
|---|---|
| < 100 ms | 优秀，可放心做实时体感控制 |
| 100–160 ms | 可用，体感手感正常，快速动作略有滞后 |
| 160–250 ms | 偏慢，闪避类操作有延迟感，需要预测补偿 |
| > 250 ms | 太慢，不适合直接驱动玩法，要改成「本机录制 + 事后对齐」 |

这个阈值直接决定第 2 步（体感控制）和第 3 步（基础游戏）怎么做，
所以它是第 1 步最值钱的一个数字。

### 关于测量精度

卡片每帧重画一次，所以量到的值天然含「0 ~ 一个刷新周期」的量化偏置，
平均偏高半个周期。工具会同时打印**原始值**和**扣掉偏置的估计值**，
以后者为准（例如卡片 30fps 刷新时，偏置约 16ms）。
另外量的是「绘制 → 该帧回到电脑内存」，比严格意义的「glass-to-glass」略保守（偏大），
用来判断「能不能玩」是安全的方向。

## 三、网页端 360° 拖动预览（无畸变）

```bash
open -n "$PWD/X5Link.app" --args web --open
# 或在 bundle 里跑：python -m x5link web --port 8765
# 然后浏览器打开 http://127.0.0.1:8765/

# 停止服务（关浏览器标签不会停它，服务在后台继续跑）
pkill -f "m x5link web"
# 嫌占资源/想更流畅：把推流降到 1280x640
open -n "$PWD/X5Link.app" --args web --stream-scale 1280 640
```

> 改完 `viewer.html` 不用重启服务，浏览器刷新一下就行（服务每次请求都重新读盘）。
> 改 `web.py` 才需要重启。

浏览器里用 WebGL 把等距柱状画面实时重投影成**正常的透视视角**：拖动看四周、
滚轮/双指缩放。看到的就不再是「中间鼓、两边拉」的鱼眼感，而是像站在现场转头
一样。右上角小窗是原始经纬图，绿框标出当前视锥落在哪一块。

快捷键：`R` 复位 · `E` 切换原始经纬图（用来对比畸变） · `F` 全屏。

**交互约定**（有回归测试 `tools/test_view_dir.mjs` 盯着，别改反）：

- **抓住画面拖** —— 画面位移方向 == 手移动方向：手向上拖，画面就**向上**走，
  图片黏在鼠标上。这是通用约定（街景 / YouTube 360 /
  [Pannellum](https://github.com/mpetroff/pannellum) /
  [Photo Sphere Viewer](https://github.com/mistic100/Photo-Sphere-Viewer) /
  [egjs view360](https://github.com/naver/egjs-view360) 都一样）。
- 它的推论容易被写错：手向上拖时，**视线其实是往下转**（因为画面在上移）。
  这里踩过坑 —— 曾经按「向上拖 = 抬头」实现，结果画面和手反着走，
  就是典型的「不跟手」。**测试断言的是画面位移，不是视线方向。**
- 灵敏度是「转过的角度 ∝ 当前视场角」：拖满整个视口高度正好转过一个 FOV。
  所以放大之后不会变成一拖就飞，缩小时也不会拖半天不动。
- 跑 `node tools/test_view_dir.mjs`（10 项断言，含一条反向验证 ——
  确认这个测试真的能抓到写反的情况）。

**为什么跟手**（这是调过一轮才对的）：

| 做法 | 结果 |
|---|---|
| 每个 rAF 都上传一次 1920×960 纹理 | ❌ 120Hz 下约 1.8GB/s，主线程全被拷贝吃掉，拖动一顿一顿 |
| **画面只在新帧到达时上传；转视角按屏幕刷新率跑** | ✅ 画面按源码率更新，视角 120Hz 跟手 |

具体实现：用 MJPEG `<img>` 的 `load` 事件当「有新帧」的信号（并留了两条保底，
不会把画面卡死），纹理直接从 `<img>` 交给 WebGL 省掉一次全分辨率拷贝；
小地图也只在画面或视角变化时才重画。

**为什么是无畸变的**：每个像素先反推一条视线方向，再用「经纬图 → 透视」的公式
去采样。这和 `3dgs-lab/x360/projection.py` 里那套已经数值验证过的投影是同一个
数学，只是搬到 GPU 上实时跑（见 `x5link/viewer.html` 里的 fragment shader），
所以不需要任何外部库，完全离线可用。

**实现要点**（都在 `x5link/web.py`）：

- ffmpeg 直接输出 MJPEG，Python 只负责切包和转发，**完全不碰 2880×1440 的原始帧**
  （否则会把实时性拖垮）。浏览器用 `<img src="/stream.mjpg">` 收流，再当纹理上传。
- **推流就是原生 2880×1440，不再缩小**；质量 `--quality`（默认 2 = 最好）。
  相机那边已经在压了，我们这层再缩一次就是白丢真实细节。
- ffmpeg 挂了会自动重拉，相机被拔掉或抢走都能自己恢复。
- 端点：`/`（查看器）、`/stream.mjpg`（MJPEG）、`/snapshot.jpg`（当前帧）、`/status`（JSON）。

**帧率与画质的天花板在哪**（实测数据，别在错的地方使劲）：

| 项目 | 实测 | 结论 |
|---|---|---|
| 相机 Webcam 模式 | `avformats` 读出只有 2 档，**都是 30fps** | 30fps 是硬件上限，提不上去 |
| 服务端推流 | **30.07 fps**（20 秒窗口，稳定） | 已经满帧 |
| 浏览器显示 | **29.75 ~ 30.0 fps** @ 原生 2880×1440 | 满帧，且没为了画质牺牲帧率 |
| 视角旋转 | 屏幕刷新率（ProMotion 120Hz） | 拖动跟手不受视频帧率限制 |

### 关键修复：JPEG 解码必须放到 Worker 里

这是「网页上看着完全不到 30 帧」的真正原因，也是我绕了最久的一个坑。

**症状**：服务端明明稳定推 30fps，但浏览器里实测显示帧率是
`28.97 → 24.0 → 18.0`，而且**持续往下掉**（连 `/report` 的回报间隔都从 0.9s
拉长到 3s）。

**原因**：原来是把 `<img>` 直接交给 `texSubImage2D` 当纹理上传。只要那一帧
**还没解码完**，浏览器就会**在主线程上同步解码** —— 2880×1440 一张 20~40ms，
而 30fps 的预算只有 33ms。于是帧率被死死压在 20 上下，画面越复杂掉得越狠。
（更早我还加过一个 64×32 的像素比对探针，那个 `drawImage` 每个 rAF 又逼它
解码一次，属于雪上加霜，已删。）

**修法**（都在 `viewer.html`）：把 MJPEG 的读取和解码整个搬到 **Worker** 里 ——
Worker 自己 `fetch` 流、按 SOI/EOI 切出 JPEG、`createImageBitmap` 解码，
只把**已经解好的** `ImageBitmap` 用 transferable 传回主线程。主线程只做
「上传纹理」一件事，一次解码都不做。

**效果**（原生 2880×1440，实测）：

| | 修之前（主线程解码） | 修之后（Worker 解码） |
|---|---|---|
| 显示帧率 | 28.97 → 24.0 → **18.0**（持续下降） | **29.75 ~ 30.0**（稳定） |
| Worker 解码吞吐 | — | **30.0 fps**（6 秒 180 帧） |
| 分辨率 | 2880×1440 | 2880×1440（一点没降） |

踩过的坑记一下：**Blob URL 起的 Worker 里，相对路径 `fetch('/stream.mjpg')`
会直接解析失败**（base 是那个 `blob:` 地址，不是页面地址），必须用
`location.origin` 拼绝对地址。

> 调试手段：页面暴露了 `window.__dbg()`，可以直接问它
> `{workerAlive, gotAnyBmp, bmpCount, shownFrames, shownFps, texW, texH, lastErr}`；
> 同时每秒把实测帧率回传到 `/report`，所以从 `curl /status` 就能读到
> `browser_shown_fps` —— 不用去截用户的浏览器窗口。
> **注意**：后台标签页的 rAF 会被 Chrome 节流，此时的帧率数字没有意义，
> 必须在可见标签页里量。

> **画质瓶颈不在软件，也不在 USB 链路 —— 在 X5 的 Webcam 模式本身。**
> （这条我一开始判断错了，以下是换线后的实测纠正。）
>
> 起初 `ioreg` 读到 `UsbLinkSpeed = 480000000`（USB 2.0），我据此推断是带宽不够、
> 相机被迫狠压。于是换了 USB 3 线，链路确实升上去了：
> `UsbLinkSpeed = 5000000000`（5 Gbps）、`Device Speed = 3`。但画质**纹丝不动**：
>
> | 条件 | 单帧 | bit/像素 | 锐度(拉普拉斯方差) |
> |---|---|---|---|
> | 换线前（USB 2.0，480 Mbps） | 336 KB | 0.66 | 63.2 |
> | 换线后（USB 3.0，5 Gbps） | 315 KB | 0.62 | 74.4 |
>
> 两个数都在噪声范围内。**X5 的 Webcam 模式是按固定质量编码的，带宽再宽也不用。**
>
> 佐证：无损抓一帧（PNG）有 2.4 MB，而我们 q=2 重编码只有 315 KB —— 差的那些体积
> 主要是相机压缩带来的伪影和噪声，不是真实细节。1:1 看边缘是平滑渐变的，
> 没有锐利的高频信息，说明细节在相机那一侧就没有了。
>
> 所以结论：
> - **实时画面就到这个水平为止**（Webcam 模式是为视频会议调的，不是给后期用的）。
>   值得一试的是翻一下相机机身的 Webcam 设置，看有没有画质档位可选。
> - **要高画质素材，走相机本机录制**（8K）—— 这也正是第 5–7 步
>   （高光 / 漫画册 / 海报）本来就需要的来源。实时流只负责交互，不必也不该
>   承担出片画质。

> 实测：2880×1440 采集 → 1920×960 推流，浏览器渲染 120fps（ProMotion），
> 画面与经纬图小窗同步更新。
>
> 如果相机正对着显示器，会看到「画面里套画面」的无限回授 —— 这是正常物理现象，
> 把相机转开、或者缩短相机到屏幕的距离就能避开。

## 四、「能否同时保存录像」怎么验

原文这一步有歧义，它其实问的是两件事，要分开答：

**1. 电脑侧：预览的同时能不能存素材？**
✅ 能，**已实测通过**。`preview --record` 会同时起两个独立的 ffmpeg：一路全画质
直写 mp4（Python 完全不碰它），一路只把缩小的帧吐给预览。实测 2880×1440：
录出 322 帧 / 10.35 秒，**时间轴与真实时间一致**，预览同时稳定跑在 ~29fps。

> 这条路踩过两个坑，都写进代码注释了：
> ① 让**一个** ffmpeg 同时输出「管道 + 文件」，会因 avfoundation 报的假时基
> （1000k fps）触发无限补帧 —— `dup=71799`、时间戳卡在 0、进程最后卡死；
> ② 反过来让 Python 中转全画质帧（12.4MB/帧）又会掉到 ~12.5fps，而且录出来的
> 视频被时间压缩，**会让第 5 步「事件时间 ↔ 真人片段」对不上**。
> 所以最终方案是「两个进程，各干一件事」。

**2. 相机侧：在 USB 摄像头模式下，能不能同时往 SD 卡录原片？**
⏳ **需要实测**，官方文档没有明确写。步骤：

1. 相机进入「USB 摄像头」模式，电脑上 `preview` 能看到画面
2. 按相机机身的录像键，看是否开始录像、相机屏幕是否出现录制计时
3. 录 10 秒后停止，把卡插回电脑看有没有新文件

**预期是「不行」**。USB 模式是一个互斥的模态（选了摄像头模式，相机就不在录像模式），
官方文档也始终把 webcam 场景描述成「电脑端负责采集/推流」。如果实测确实不行，
架构上要接受一个取舍：

- **要实时画面** → 素材只能用电脑录的那份 UVC 流（`preview --record`），
  画质受 webcam 模式限制（2880×1440、约 30fps、压缩过）
- **要高画质原片** → 只能让相机本机录，但那样电脑就拿不到实时画面，
  第 3 步的实时玩法就不成立

这个取舍会影响第 5–7 步（高光、漫画册、海报）的素材质量，建议实测后尽早定下来。

## 五、权限（重要）：必须通过 X5Link.app 启动

**这条最关键** —— 直接跑命令是打不开摄像头的，必须套一层 `X5Link.app`。

原因：本会话的进程链是 `launchd → node(裸二进制) → bash`，**没有任何 App bundle
身份**，macOS 的 TCC 无法把「摄像头权限」归给它，于是既不弹授权窗、也永远不授权
（打开设备要么直接失败，要么卡住）。而且 OpenCV 申请权限的方式是「发个请求然后
死等」，它把主线程 run loop 堵住了，弹窗根本没机会出现。

`X5Link.app` 就是为解决这个做的壳，里面有两块原生代码（源码在 `tools/`）：

| 文件 | 作用 |
|---|---|
| `tools/perm.m` → `Contents/MacOS/X5Link` | 先把自己变成**真正的 GUI App**（`NSApplication` + activate），再**一边转 run loop 一边等**授权结果，弹窗才出得来。拿到权限后把 python 工具作为**子进程**拉起（不 exec，保持 bundle 为父进程，TCC 才认这个身份）。 |
| `tools/avformats.m` → `Contents/Resources/avformats` | 直接问 AVFoundation 要相机暴露的全部采集格式（OpenCV 不会枚举，本机 ffmpeg 又砍掉了 `-list_formats`）。 |

用法：

```bash
open -n "$PWD/X5Link.app" --args <子命令> [参数...]

open -n "$PWD/X5Link.app" --args preview --record ~/Desktop/run01.mp4
open -n "$PWD/X5Link.app" --args web --open

# 调试后门：把后面整串当命令原样执行（例如直接试 ffmpeg 参数）
open -n "$PWD/X5Link.app" --args --exec ffmpeg -f avfoundation -video_size 2880x1440 -i 0 ...
```

输出写到 `x5link-app.log`（用 `open` 起的进程看不到终端输出）。

> **改 bundle 里的文件要重新签名；而重签名会让 ad-hoc 代码哈希变化，
> macOS 就把之前给的摄像头授权作废、重新弹窗。**
> 所以：**改 Python 代码不用重签**（`x5link/*.py` 在 bundle 外面），只有改
> `Info.plist` / `run.sh` / 那两块原生程序才需要：
>
> ```bash
> clang -fobjc-arc -O2 -framework AVFoundation -framework AppKit -framework Foundation \
>   -o X5Link.app/Contents/MacOS/X5Link tools/perm.m
> clang -fobjc-arc -O2 -framework AVFoundation -framework CoreMedia -framework Foundation \
>   -o X5Link.app/Contents/Resources/avformats tools/avformats.m
> codesign --force --sign - X5Link.app
> ```

- **屏幕录制权限**：只有想把「屏幕采集」当假相机做回环测试时才需要，正常用 X5 不需要。
